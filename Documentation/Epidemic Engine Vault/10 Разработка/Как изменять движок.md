# Как правильно изменить движок

Вначале определите authoritative owner и публичный контракт. Изменяйте минимальный набор C++ файлов, не вводя новую dependency edge до проверки архитектурных правил. Если требуется техническая связь Runtime majors, реализуйте port/adapter в `Runtime/Support`. Для игровых связей используйте Framework IntegrationLayer.

Порядок работы:

1. Через [[11 API/Индекс API]] найдите public header и module `CMakeLists.txt`.
2. Прочитайте [[02 Архитектура/Граница игрового кода]] и [[02 Архитектура/Правила архитектурного freeze]].
3. Найдите существующие tests и зафиксируйте ожидаемую семантику и негативные входы.
4. Измените owner и соответствующие реализации с минимумом переносов responsibility.
5. Добавьте/исправьте адресные unit и integration tests; убедитесь, что негативная проверка обнаруживает ошибку.
6. Соберите changed targets и адресные tests, затем нужную полную матрицу.
7. Обновите public docs и source-of-truth evidence, не подменяя `PARTIAL/UNKNOWN` на `PASS`.

Изменения не должны создавать вторичные authoritative caches, терять leases при failure или нарушать transaction boundaries. [[10 Разработка/Процесс изменения]] · [[09 Качество и статус/Матрица проверок]].

## Правильная последовательность исправления

Начните с owner, чей authoritative state или контракт реально нарушен. До реализации запишите воспроизводимый вход и наблюдаемый неправильный выход. Сопоставьте публичную операцию с её `.cpp`, CMake target и тестовой регистрацией. Изменения в инфраструктурном Support оправданы только если ошибка касается нейтрального cross-major wiring; доменную gameplay семантику помещайте в Framework owner/integration layer.

Пишите тест на минимальный существенный контрпример до изменения логики. Для mutator это обычно old snapshot/revision, инвалидный вход или fault-injection, вызов и последующая проверка, что состояние не частично применилось. Для cleanup проверяйте повтор после неуспешного release, сохранение lease и отсутствие двойного освобождения. Для AI/Simulation дополнительно проверяйте стабильность порядка и однозначность принятых решений при одинаковых входах.

После исправления запускайте адресный target, dependent integration test, architecture/header checks при изменении границы, затем полную квалификацию на одной версии исходников. Обновляйте контрактную документацию того же owner одновременно с кодом. Если proof не удалось выполнить на текущей среде, укажите `NOT RUN` с конкретной причиной, не подменяя его `PASS`.

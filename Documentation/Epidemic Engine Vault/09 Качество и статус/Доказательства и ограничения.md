# Доказательство корректности и ограничения

Принцип проверки движка большой кодовой базы: для каждого поведения явно определяются owner, observable API, положительная фикстура, отрицательный контроль, fault paths, threading, ownership, persistence и deterministic replay (когда применимо). Тест должен падать при целенаправленно внесённом нарушении; иначе его результат не является достаточной защитой.

Разделяйте:

1. **Source inspection**. Подтверждает структуру и доступность объявлений.
2. **Compilation**. Подтверждает корректность C++ и link на данном toolchain.
3. **Unit/integration runtime test**. Проверяет наблюдаемое поведение на конкретных inputs.
4. **Audit capture**. Подтверждает отдельно указанный scope, tool activation и provenance.
5. **Milestone acceptance**. Полный перечень требований с независимым review и обнаруженными limitations.

Документы milestone могут содержать исторические результаты, которые утрачивают применимость после локальных изменений. Для выводов о текущем build необходимо новый проверенный Run.

---

## Стандарт приемлемого утверждения

Для каждой проверки сохраняйте command, tree fingerprint, Windows toolchain, build path/profile/configuration, registered test count, count executed, exit status и артефакты. Пометки `PASS`, `FAIL`, `UNKNOWN`, `INCOMPLETE` относятся к точному test/observation scope. Непрошедший тест, недоступный backend или отсутствующий raw trace не должны быть оформлены как зелёные результаты.

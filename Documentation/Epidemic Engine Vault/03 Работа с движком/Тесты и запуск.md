# CTest и запуск тестов

Тесты регистрируются при `BUILD_TESTING=ON`; исполнение Windows-oriented бинарников требует рабочей Windows среды. Само наличие CTest target не доказывает, что тесты прошли на текущем дереве.

```powershell
ctest --test-dir build/full-debug -C Debug --output-on-failure --no-tests=error

# Список имен и label'ов текущего build tree
ctest --test-dir build/full-debug -C Debug -N

# Адресная регрессия Runtime
ctest --test-dir build/full-debug -C Debug -R EpidemicRuntime --output-on-failure --no-tests=error

# Не использовать -R для объявления полного acceptance
```

Для CMake target на отдельных уровнях: `cmake --build build/full-debug --config Debug --target EpidemicPublicHeaderSelfContainment --parallel`. Негативный architecture self-test вызывается `cmake -P cmake/ArchitectureFreezeSelfTest.cmake`.

Проектный скрипт `Invoke-Dev.ps1 -Action Full` выполняет clean полную матрицу данного профиля, архитектурную проверку, header self-containment, CTest, `Verify-Changed -Mode Deep` и `git diff --check`. Это гораздо более широкий gate, чем один локальный тест. См. [[09 Качество и статус/Матрица проверок]].

### Рекомендации для исправлений

Сначала воспроизведите точное падение, затем меняйте owner и запускайте адресные тесты. После cohesive изменений прогоняйте зависимые тесты, перед квалификацией по milestone повторяйте полную матрицу на зафиксированном дереве. Не путайте CI smoke с полной физической квалификацией Auditor.

## Как выбрать минимально достаточный прогон

После изменения локальной функции сначала соберите владеющую библиотеку и соответствующий адресный тест. Затем пройдите тесты зависимых модулей, header self-containment и architecture checks, если изменялась публичная поверхность. Для изменения cross-major Support дополнительно проверьте интеграционный сценарий, отказ на промежуточной фазе и повторный shutdown. Для утверждения о закрытии milestone необходимы заранее определённые полные gates на одном неизменном дереве.

```powershell
# Проверить, что тест действительно зарегистрирован, прежде чем применять -R.
ctest --test-dir build/full-debug -C Debug -N
# Локальная Runtime Scene регрессия, если target зарегистрирован в конфигурации.
cmake --build build/full-debug --config Debug --target EpidemicRuntimeSceneTests
ctest --test-dir build/full-debug -C Debug -R '^EpidemicRuntimeSceneTests$' --output-on-failure --no-tests=error
# Увидеть подробные причины провала, не скрывая отрицательный exit code.
ctest --test-dir build/full-debug -C Debug --output-on-failure --no-tests=error
```

Регистрация тестовых executable и CTest names может различаться, поэтому перед строгим `-R` используйте `ctest -N`. Ведение журнала включает target, фактическую команду, абсолютный build path, конфигурацию, commit/tree fingerprint, начало/окончание и полный exit code. Повторный запуск без изменения входных данных не добавляет независимых доказательств прохождения иных scope.

## Негативные сценарии важнее обычного smoke

При проверке `Result` failure проверяйте отсутствие частично принятых mutators. Для snapshot/restore проверяйте отказ на плохом snapshot при сохранении старого live state. Для `Scene` проверяйте `KeepLocal`, `KeepWorld`, cycle reject и нежизнеспособный world transform. Для `Resources` проверяйте failed lease release и lifetime payload. Для `Auditor` проверяйте битые события, утрату трассы и невозможность ложного COMPLETE/PASS. Негативный тест считается полезным, когда он падает при намеренном нарушении закреплённого условия.

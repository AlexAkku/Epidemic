# Ошибки, Result и инварианты

`foundation::Result<T>` описывает ожидаемые recoverable failures: невозможность создать окно, загрузить payload, обработать данные или завершить транзакцию. Нарушение программного контракта (двойная регистрация сервиса, недопустимый lifecycle, цикл зависимостей) квалифицируется отдельно; assertions/exceptions не обязаны быть представлены как normal runtime failure.

Runtime coordinator различает fatal-level contract error `Tick()` и локальную recoverable ошибку major, включаемую в `RuntimeTickResult.failures`. После локальной ошибки независимые фазы продолжаются. Диагностику необходимо читать вместе с `executed_steps`, provenance и текущим lifecycle.

Для Auditor крайне важно различать `COMPLETE` захват, `PASS` проверку, `UNKNOWN` отсутствие измерения и `INCOMPLETE` утрату информации. [[08 Auditor/Понимание evidence]].

Первоисточник error policy: [[90 Первоисточники/Documentation/policies/error_exception_policy|error_exception_policy.md]].

## Точное значение возвращаемых ошибок

`foundation::Result<T>` хранит либо успешный `T`, либо `foundation::Error`; `operator bool()` проверяет успешность. `Value()` при неуспехе бросает `std::runtime_error`, `GetError()` при успехе также бросает. Для `Result<void>` применяется тот же принцип. Само наличие `noexcept` или `Result` не означает отсутствия всех внутренних исключений; exception policy задаётся на границе владельца.

```cpp
const auto result = runtime.scene->nodes->CreateNode();
if (!result)
{
    const auto& error = result.GetError();
    // Логирование error зависит от public API error.h.
    return; // Для callback/void-контекста.
}
const auto node_id = result.Value();
```

Пример демонстрирует обработку `Result` и предполагает, что `runtime.scene` доступен и создан. Не используйте `Value()` как способ проверки. При ошибке ожидается реакция вызывающего слоя: retry, отмена операции, сообщение пользователю или остановка кадра согласно контракту конкретного API.

## Сценарии отказов для обязательных проверок

Проверяйте повторные/неверные IDs, дубли в реестрах, циклическую иерархию, NaN/Inf, exhaustion revisions, allocation failures, ошибки внешних callback и partial resource cleanup. В Scene отказ reparent не должен менять дерево или revision; в Support позднее исключение после принятой фазы не должно повторно выполнять уже принятый prefix; в Auditor повреждение evidence не должно превращаться в `PASS`.

Фактические error-code литералы и их строки приведены на страницах модулей. Обобщённое правило не даёт права распространять гарантию atomic mutation на любой новый интерфейс без собственного теста.

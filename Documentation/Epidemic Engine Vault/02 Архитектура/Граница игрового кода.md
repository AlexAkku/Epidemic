# Граница игрового кода

Выбор места для нового кода определяется владельцем semantics и authoritative state.

| Что реализуется | Где должно жить | Обоснование |
| --- | --- | --- |
| Win32 окно, источник ввода, scheduler | `EngineBase` | Нейтральная инфраструктура исполнения |
| Resource leases, Scene, Physics, Renderer, Streaming | `EngineRuntime` | Нейтральные engine contracts |
| Общая логика инвентаря, NPC, диалогов, фракций, боя | `EngineFramework` | Переиспользуемые игровые понятия |
| Контент, баланс, конкретные правила и сценарио | `Game` | Конечная игра |
| Техническая связь между Runtime majors | `EngineRuntime/Support` | Typed adapter, без игровой семантики |
| Gameplay связь между owners | `EngineFramework/IntegrationLayer` | Оркестрация без новой копии state |

Пример: физический контакт создаётся в Runtime Physics, применение урона конкретному персонажу принадлежит игровому owner/интеграции. Тип `RuntimeObjectId` используется для сопоставления, игровая сущность не записывается в Runtime.

На новые горизонтальные связи распространяются правила `cmake/ArchitectureFreeze.cmake` и `EngineFramework/DevelopmentInfrastructure/cmake/FrameworkArchitecture.cmake`. Не подменяйте архитектуру удобными `#include` из соседних majors.

---

## Решение о размещении новой функциональности

Gameplay state и domain commands помещайте в соответствующий EngineFramework owner; neutral adapter для scene/physics/render/resource находится в Runtime Support; платформенное окно, ввод и RHI принадлежат EngineBase. До добавления нового include проверяйте CMake graph и who-owns-what contracts. Новый gameplay feature не должен заставлять EngineRuntime знать об Inventory, Combat или Economy.

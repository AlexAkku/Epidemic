# Владение состоянием и идентификаторы

`authoritative state` принадлежит конкретному owner. Derived/read-model может быть пересчитан, но не должен изменять чужой state обходным путём. В EngineRuntime `World` управляет логическим размещением/reality/residency, а `Scene` управляет hierarchy и пространственным представлением. Gameplay World и records EngineFramework добавляют смысл и используют IDs для связи.

Типичные границы:

* `ResourceHandle` служит для запроса состояния/содержимого; `ResourceLease` является основанием ownership, нужным для освобождения.
* `RuntimeObjectId` сопоставляет runtime-представление и gameplay record без переноса gameplay-полей вниз.
* Physics world transforms передаются через Support projection queue; публикация в Scene проходит отдельной phase.
* Simulation предлагает mutations через proposals/commit port, не пишет прямо в произвольные domain owners.
* Persistent data фиксируется через версии, snapshots, transactional границы и соответствующие owners.

Цель этих правил: не допускать двойного владения, повторного выполнения принятого префикса операций при retry и незамеченных partial commits. [[07 Сценарии/Игровое состояние и идентификаторы]] · [[07 Сценарии/Сохранения и детерминизм]].

## Где хранится authoritative state

У каждого owner должен быть один источник истины. Gameplay entity identity, инвентарь, экономические данные и правила живут в соответствующих EngineFramework owners. Runtime World содержит runtime placement/residency, Scene содержит иерархию и пространственные трансформации, Physics содержит собственное расчётное представление. Render proxy, spatial index, кадры анимации и кеши являются derived state; их можно перестраивать из признанного authoritative state согласно соответствующим contracts.

Ревизия не всегда означает версию всего движка. Например, `ISceneNodeRegistry::GetRevision()` наблюдает изменение Scene, а `World` использует собственные revisioned commands. Нельзя переносить локальный `expected_revision` одного owner в другой. `SceneNodeId`, `GameplayObjectRef`, `RuntimeObjectId` и resource identifiers принадлежат разным доменам; совпадение числовых представлений не даёт права заменять один тип другим.

## Разработка mutation без частичного commit

1. Проверить валидность ID и входных значений, текущую ревизию, принадлежность объекта owner и допустимый lifecycle.
2. Вычислить зависимые изменения во временной структуре: индекс, sibling/parent links, очереди, журнал, генератор ID.
3. Выполнить все потенциально падающие аллокации и вызовы внешних портов до authoritative publication, если контракт этого требует.
4. Опубликовать подготовленное состояние. Только после успешной публикации менять observable revision и журнал.
5. Для retry сохранить неподтверждённые ownership entries, не воспроизводя уже принятый prefix операций.

Это общий ориентир. Конкретная atomicity boundary различается между модулями: `Scene` валидирует весь затрагиваемый subtree до reparent, `Runtime Support` сохраняет pending phase и leases, Framework owner валидирует snapshot до `RestoreSnapshot`. При изменении требуется подтверждать контракт отдельным негативным тестом на отказ посередине транзакции.

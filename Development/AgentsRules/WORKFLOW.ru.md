# Как агент работает с Epidemic

## Вход в проект и источники требований

Сначала агент читает корневой `AGENTS.md`, затем `Development/AgentsRules/AGENT_RULES.md`. Последний файл является единым контрактом выполнения работ. Текущий запрос пользователя определяет объём работы и имеет приоритет. Если пользователь явно указывает конкретную задачу в `Development/Tasks/`, агент читает её; самостоятельно просматривать каталог задач нельзя.

Порядок источников для понимания реализации: текущая задача, действующий production-код и тесты, `Documentation/architecture.md`, остальные актуальные документы. Исторические отчёты и старые milestone-файлы не подтверждают текущее состояние. `.ai/` содержит только восстанавливаемые рабочие данные и не задаёт требования. Над проектом работает один рассуждающий агент; компиляторы и локальные инструменты могут использовать собственные потоки.

До изменений агент смотрит состояние Git и фиксирует для себя уже существующие изменения. Чужие изменения сохраняются. Удалённые файлы не восстанавливаются автоматически, неотслеживаемые каталоги не добавляются в Git без необходимости. `Development/AgentsRules/` меняется только при запросе, затрагивающем инструменты или сам процесс разработки.

## Как я понимаю архитектуру

Порядок слоёв от нижнего к верхнему: `EngineBase -> EngineRuntime -> EngineFramework -> Game`. Разрешённые зависимости направлены сверху вниз: `Game -> EngineFramework -> EngineRuntime -> EngineBase`. Название слоя в архитектурном описании — GameFramework; каталог реализации — `EngineFramework`. Нижний слой не включает верхний и не связывается с ним через CMake.

`EngineBase` обеспечивает базовое исполнение приложения и платформенные механизмы. `EngineRuntime` содержит нейтральные переиспользуемые подсистемы движка. `EngineFramework` добавляет общие игровые понятия, а конкретные правила и контент принадлежат Game. Детали компонентов и утверждённые границы изучаю в актуальной архитектурной документации и рядом с исходниками. Существующие allowlists нельзя расширять ради прохождения проверки.

Границы проверяет `cmake/ArchitectureFreeze.cmake`: зависимости targets, production includes и самодостаточность public headers. Отрицательные fixtures в `cmake/ArchitectureFreezeSelfTest.cmake` проверяют, что запрет действительно срабатывает. Текст документации объясняет намерение, а код проверок и текущие тесты показывают исполняемый контракт.

## Навигация по коду

Для известного текста, идентификатора или сообщения ошибки использую `rg`. Для известного C++ символа и его definition/references/callers/type использую clangd MCP. Для структуры сборки читаю нужный CMake-файл и выполняю точечный поиск.

Семантический retrieval использую, когда точное местоположение поведения неизвестно и обычный поиск недостаточен. По умолчанию получаю три результата. Retrieval помогает найти код, но не доказывает его корректность. Индекс охватывает актуальный код движка, тесты, исходники аудитора и CMake; задачи и исторические отчёты в корпус не входят. При запросе сравниваются хеши содержимого файлов с индексом, затем обновляются изменённые, новые и удалённые элементы в SQLite, FTS и памяти daemon. Постоянного watcher нет.

После изменения CMake или списков исходников обновляю compilation database до использования clangd/static analysis. Инструмент выбирается по вопросу: не прогоняю несколько поисковых систем подряд, если первая уже дала ответ.

Читаю небольшие диапазоны: обычно до трёх диапазонов и 200 строк за шаг, при углублённом исследовании до пяти и 400 строк. Большие JSON, таблицы, логи и diff целиком не вывожу. Уже изученную подсистему не перечитываю полностью; возвращаюсь только к изменённым диапазонам или по новым данным. При успешной проверке достаточно статуса, длительности и пути лога; при ошибке сначала читаю краткую диагностику.

## Реализация и локальные проверки

Работа идёт связными пакетами: обычно две–пять изменений одной подсистемы. Сначала изучаю минимально необходимый код и существующие тесты, затем выполняю весь пакет, после этого запускаю проверку, способную обнаружить ошибку в изменённом поведении.

При воспроизведённом дефекте сохраняю один сильный regression test, который падает до исправления и проходит после него. Для простой правки документации отдельный тест обычно не нужен; если существующий тест проверяет путь документации, обновляю и запускаю его. Не создаю постоянную инфраструктуру для разового исследования — временные скрипты лежат в `.ai/tmp/`.

Обычные configure/build/test выполняются через `Invoke-Dev.ps1`, долгие и шумные команды — через `Run-Quiet.ps1`. Последний сохраняет логи, ограничивает память и время, владеет деревом дочерних процессов через Windows Job Object и завершает только принадлежащие ему процессы. Для тяжёлой работы сохраняются минимум 4 GiB свободной физической и виртуальной памяти; обычный верхний лимит job — 8 GiB. Независимые тяжёлые задания не конкурируют за один бюджет памяти или одинаковые выходные файлы.

```powershell
Development/AgentsRules/Scripts/Invoke-Dev.ps1 -Action Configure -Profile full -Configuration Debug
Development/AgentsRules/Scripts/Invoke-Dev.ps1 -Action Build -Profile full -Configuration Debug -Target RelevantTarget
Development/AgentsRules/Scripts/Invoke-Dev.ps1 -Action Test -Profile full -Configuration Debug -TestRegex RelevantTest
Development/AgentsRules/Scripts/Verify-Changed.ps1 -Mode Fast
```

Profiles `base`, `runtime`, `full` выбирают слой сборки. `Verify-Changed.ps1` анализирует изменённые C++ translation units на границе пакета, а не после каждого редактирования. Изменения headers дополнительно требуют сборки затронутых потребителей: список изменённых `.cpp` сам по себе этого не доказывает.

## Итоговая проверка

Порядок работы: реализация пакетами → focused tests → semantic review итогового diff → исправления и затронутые focused tests → freeze → одна финальная qualification. Все изменённые production/build/test/tool файлы просматриваю небольшими диапазонами до freeze. Затем выполняю требуемые configure/build, тесты, постоянные проверки архитектуры и contracts, необходимый static analysis и механическую проверку Git diff/status.

```powershell
Development/AgentsRules/Scripts/Invoke-Dev.ps1 -Action Full -Profile full -Configuration Debug -Clean
```

Если найден дефект, исправляю его и повторяю затронутые проверки и финальный gate. Прохождение одной focused-проверки не объявляю доказательством полной работоспособности движка. В результате перечисляю внесённые изменения, реально выполненные проверки и конкретные блокеры. Не создаю цепочки receipts и evidence-ledgers ради подтверждения самого подтверждения.

## Установка и размещение данных

Постоянные исходники, шаблоны и конфигурация процесса находятся в `Development/AgentsRules/`. Установка запускается через `Scripts/Setup-AgentTools.ps1`; скрипт проверяет системные инструменты, разворачивает закреплённый clangd MCP, Python-окружение retrieval и project config. Закреплённая ревизия MCP получает воспроизводимое Windows-исправление аргументов clangd, SDK `1.31.0` и совместимые исправления runtime-зависимостей; зависимости для компиляции удаляются из развёрнутого runtime после сборки. `Doctor.ps1` проверяет наличие зависимостей. Модели переиспользуются локально; автоматические нейронные загрузки в setup отключены.

Системные Git, Visual Studio C++/Windows SDK, LLVM, CMake, Ninja, Node, Python, ripgrep, cppcheck и Ollama используются из установленных locations. Проектные скачиваемые инструменты и зависимости размещаются в `.ai/`, без создания `node_modules` в корне проекта. Graft, Repomix и отдельный Enforcer не входят в текущий основной pipeline.

```text
build/
  full-debug/       C++ сборка полного движка
  runtime-debug/    C++ сборка Runtime
  base-debug/       C++ сборка Base
  clangd/           CMake/Ninja configure и compile_commands.json для clangd
  auditor-native/   C++ сборка native-части аудитора
.ai/
  tools/            проектные инструменты и runtime bundle аудитора
  retrieval/        .venv, модели и SQLite semantic index
  venv/             Python-окружения инструментов
  auditor/          результаты аудитора и его SQLite
  cache/            npm, pip, Hugging Face, Torch caches
  logs/             текущие логи команд
  tmp/              временные файлы
  state/            необязательная краткая заметка текущей сессии
```

В `build/` находятся только CMake/компиляторные сборки, включая native Auditor; инструменты читают `build/clangd/compile_commands.json` напрямую. `Reset-AiWorkspace.ps1` удаляет только `.ai/`; `build/` очищается отдельно. Постоянные инструкции, исходники инструментов, setup и шаблоны остаются в `Development/AgentsRules/`. Setup восстанавливает конфигурацию, инструменты и venv; модели и первичное индексирование требуют отдельного ручного запуска. При ручном запуске приложений выбираю `.ai/` рабочим каталогом, если приложение пишет относительные логи.

## Безопасность привилегий

Привилегированные операции выполняются с минимально необходимыми правами через узкие аутентифицированные интерфейсы. Не повышаю права всего приложения и не ослабляю ACL ради обхода ошибки. Проверяю права и состояние процессов только в пределах запроса; завершаю только процессы с подтверждённым владением. Протоколы, deployment и пути конкретных компонентов описываются рядом с их исходниками.
